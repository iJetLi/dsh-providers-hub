fix(raccoon): 回环接收端必须在流程落定时关掉 + 换码失败必须落定

PR #107 自审抓出的两个真缺陷（本 PR 未合并，一并修掉）：

🔴 A（安全漏洞）：回环接收端在流程结束后**继续开着**，且仍会用真凭据换码。
  授权码是一次性凭据，而敞开的接收端就是「凭据交换漏洞」——这正是本 PR 自己
  在注释里写的那句话，但收尾没做到。
  - 根因：result 落定后只关本地页服务器（既有契约），没有关回环接收端 ——
    那句只在 close() 里，而 close() 全仓无人调用（jet-hub-rpc.ts 根本没有
    raccoonStarted.close()）。
  - 实测：流程已用短信登录成功落定后，往还活着的端口投递一枚 code ⇒ HTTP 200，
    且真的向上游发了一次换码请求（login_with_authorization_code 计数 = 1）。
  - 后果：任何本机进程都能在 5 分钟窗口内向那个端口投递一枚 code，把凭据换成
    它自己的账号 —— 而用户以为流程已经结束了。state 挡不住：state 是公开的
    （在 URL 里、也在授权页的上下文里）。
  - 为什么第一版没抓到：只测了「取消」与「流程超时」，没测「流程因别的路径
    落定」—— 而那正是真实场景（授权等待中，用户改用短信登录成功）。
  - 修法：result 落定的收尾里 cancel() 掉接收端（与关本地页服务器同一处 ——
    它们是两件独立的事，而后者才是凭据入口）。
  - 判据行为级：断言「那个端口还在不在」，不是源码文本断言。

🔴 B（UX 死锁）：换码失败时 result 永远悬挂。
  只写 state.authorizeStatus='failed' 而没有 settleErr ⇒ jet-hub-rpc.ts 里的
  raccoonStarted.result.then(...) 永远不跑 ⇒ 占位账号条目永远留着、前端
  login.poll 一直转圈到它自己的 5 分钟上限，而页面那边已经显示了「授权码已
  失效」⇒ 两边症状不同形，用户无从判断到底成没成。
  修法：换码失败走 settleErr（带原因词，不带报文）。

另三条次要：删死字段 authorizeCredential（它还驻留着完整凭据）；补回调 URL
总长上限；补 maxConnections / headersTimeout / requestTimeout / socket 超时
（官方接收端全都有）。

⚠️ 两条「够不着」的教训如实登记：
- URL 总长上限取 4096 而非官方 8192 —— Node 的 maxHeaderSize 在 URL 长到约
  8160 就先回 431 ⇒ 任何长于 8192 的 URL 根本到不了处理器 ⇒ 写 8192 等于一条
  永远走不到的死代码。
- socket 超时必须可注入（options.socketTimeoutMs）—— 20 秒默认值在单测里没法
  等 ⇒ 没有注入点那条判据就够不着。

iamToken.js）是权威，本仓实现与它逐条一致；iss 已用真实凭据复验
